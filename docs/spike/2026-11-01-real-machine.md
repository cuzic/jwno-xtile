# 実機検証（Windows 11、実ハードウェア）2026-11-01

対象: dragonflyg4（Windows 11、1920x1256 の 1 画面）。clipwire 経由で `spike/real/` のハーネスを実行。
Jwno はビルド成果物（`build-jwno.yml`）。安全策: 専用の新しい仮想デスクトップの中だけで動かし、前後で
ユーザーの窓を比較し、作った窓は WM_CLOSE で閉じる。全 5 回の実行で、ユーザーの窓は変化なし。ただし**空の専用デスクトップでしか動かしていない**: `adopt-existing!` は、ユーザーの実際のデスクトップ（最大化した窓、Explorer、ブラウザ、UWP、副モニタ）に対して一度も走っていない。

## 経過

## 見つかったこと
1. **Jwno は起動時に、フォーカスのある窓しか管理しない。** それ以外の既存の窓は、フォーカスされるか新しく開くまで
   Jwno の木に入らない（`win.janet` に起動時の走査が無い）。ホスト CI は、テスト用の窓がたまたま前面だったので通っていた。
   → アダプタが `start` で UI Automation のデスクトップ直下の窓を列挙し、Jwno の `:window-opened` に渡す
   （`adopt-existing!`。フィルタとフックは Jwno が通常どおり適用）。契約テストは、N0 が前面でない状態で CT-3 を測る。
   副作用（**未検証**。Opus M1）: 実デスクトップでは普段の窓も全てタイル対象になる。最大化した窓は Jwno の transform が解除する。副モニタの窓も主モニタにタイルされる。補助窓が空の枠になる恐れ。
2. **フォーカスの失敗はハーネスの問題だった。** 別プロセスの `SetForegroundWindow` はフォアグラウンドロックで拒否される。
   前面スレッドへ `AttachThreadInput` してから呼ぶと通る（`setfg=True`、非管理者）。アダプタの `:focus` は最初から動いていた。
3. **Jwno の `wm :desktop-name-changed` が、新しい仮想デスクトップへの切替で届かないことがある。** 届かなければ
   `wm :set-focus` も呼ばれず、A の抑制は 0 回になる（CT-13b を「最大 1 回」に緩和）。窓の管理はポーリング（窓ごとの
   `IsWindowOnCurrentVirtualDesktop`）で追従し、CT-12a/b/c は 8〜10 秒待った後の判定で通る。**ポーリングの間（最大 2 秒）の挙動は未検証**で、その間に focus を出すと元のデスクトップへ引き戻される恐れがある（Opus M2）。
4. **合成ドラッグは、この実機ではタイトルバーの移動ループを始めない**（CT-17b/c/d/f/g。イベント 0 件、窓は動かない）。
   `mouse_event` の絶対移動でも同じ。管理者権限の問題ではない。アダプタのドラッグ検出（SetWinEventHook）は
   ホスト CI で検証済みだが、**実機では未検証**。手動で確認する（下記）。

## 実機で確認できたこと
- CT-5: place で窓の見える枠がコアの矩形と 0 px 差で一致（DWM の枠）。CT-6: Jwno の retile が `:swp-flags` で止まる。
- CT-7: 最大化したタイルはフロートになる。CT-8: 最小化・復元がコアに届く。
- CT-9/10/10b: OS のフォーカスがコアに届き、`focus-next` が実際のフォーカスを動かす（Jwno の窓の `:set-focus` 経由）。
- CT-12/14: 新しく作ったデスクトップで開いた窓が管理され、元のデスクトップに戻るとタイルが戻る。**未検証**: 以前からある窓のあるデスクトップ、デスクトップの削除、park した窓を持ったままの往復。
- CT-20: ワークスペースの退避（park）と復帰、ポーリングが退避した窓を連れ戻さない。CT-21: 窓の移動（send）。
- CT-22: 終了時の復元、強制終了後の回復。

## GitHub の `windows-11-arm` ランナーの実験（2026-11-02、run 41396909844）
- イメージは `Microsoft Windows 11 Enterprise` build 26200（クライアント OS。Server ではない）。Jwno（x64 ビルド、ARM64 上でエミュレーション）は起動したが、**契約テストと sink のスパイクの設定ファイルが評価されなかった**
  （Jwno のログは `REPL server running` と `vdm-worker spawned` で止まり、`contract.log` は空）。プローブ用の設定（`--mod-path` なし）だけは動いた。
- このイメージのレジストリに仮想デスクトップの ID が無い（`VD IDs read from registry (0 bytes)`）ので、仮想デスクトップの契約テストはどのみち意味を持たない可能性が高い。
- 未解明: 起動の停止がエミュレーションの遅さか、`--mod-path` を使う設定の読み込みの問題か。実機の 1 回目の失敗（REPL ポートの衝突として解決）と同じ症状。追う価値は低いと判断し、ここで止めた（ランナーの選択肢は残してある）。
- 結論: Server ではなくクライアントの Windows 11 に近い環境は得られるが、物理入力・IME・複数モニタは再現できず、起動の問題も残る。実機の検証の代わりにはならない。
